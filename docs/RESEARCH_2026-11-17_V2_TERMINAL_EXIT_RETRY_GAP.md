## New technical finding

The deployed `/opt/securityprepper/direction-paper-executor/direction_paper.py` has SHA-256 `f4ac3f1747a8e1e6c21629fd5a9480f309af44bafb965fbe288125f7104a26a3`. `software_risk_exits()` now recognizes correctly signed shorts, checks fresh account-matched broker positions and no working orders, and attempts a day-limit buy-to-cover when `SESSION_FLAT_1340_CT` is due. However, `risk_exit_order()` derives the synthetic exit signal ID only from **entry ID + reason**, and `attempt_order()` persists one deterministic client-order ID for that tuple. Later calls refuse another broker submission for the same ID, regardless of whether the earlier limit order expired or was rejected with **zero fills**. That is correct unknown-order anti-duplication but **wrong as permanent terminal-zero-fill suppression**.

Reproducible broker-mock case: A four-share V2 short with an exact signed -4 broker position receives an accepted `SESSION_FLAT_1340_CT` buy-to-cover DAY limit at November 17 13:40 CT. The broker later reports the limit as `expired` with `filled_qty=0`, and has zero working orders. `reconcile_orders()` records `BROKER_ORDER_TERMINAL_UNFILLED`. On November 18 03:05 CT, the overdue short still exists, fresh quotes are available, but `software_risk_exits()` issues **zero additional close attempts** because it regenerates the same client-order ID. The test observed one initial mocked broker POST, no second POST, position still open. This is a **new, verified conditional implementation blocker**, not evidence that an actual DAY close has already expired.

Second broker-mock case: A DAY limit expires after **2/4 shares** filled. `reconcile_orders()` currently marks it `BROKER_ORDER_TERMINAL_UNFILLED`, with no stored filled quantity or price for that exit; the original entry remains marked fully unclosed. The broker's reduced short would then fail the safe exact-filled-quantity guard. This preserves anti-overclosing but prevents completion and misclassifies a genuine partial fill. Do not interpret this as a zero-fill or assume a remaining quantity without broker readback.

Both scenarios were replayed using local SQLite test databases and a fake broker, never real Alpaca credentials or POST. Test file: `research/test_v2_terminal_exit_retries_20261117.py`, two `@unittest.expectedFailure` cases. It ran **2 tests, 2 expected failures**, confirming that the desired recovery guarantees are not implemented. Existing safety release passed 44 separate offline tests; they did not cover these broker-terminal behaviors.

1. Reconcile previous exit by **exact broker order ID + client ID** and distinct fills (including partial fills and eventual status). A partially filled terminal order is **not** `TERMINAL_UNFILLED`. No synthetic or time-based assumptions about fills.
2. To advance one retry generation, require independently verified *terminal* old order status, exact actual filled quantity zero, no broker working orders for the symbol, complete fresh same-account position inventory still equal to strategy-owned original outstanding signed quantity, fresh quote/session/spread/holiday, and no unknown pending submission. Reserve a distinct deterministic next-attempt ID **before POST**, and never retry an unknown or still working order.
3. For partial fills, record cumulative verified buy-to-cover quantity and true remaining strategy lot, reconcile closing quantity/account inventory, enforce no unknown working orders and a single permitted next action. If any ambiguity or cross-strategy netting remains, stop automatic orders and require operator intervention.
4. Test broker rejection/cancel/expired/done-for-day, partial and out-of-order fill events, stale position, different account, own-share ownership mismatch, restart/idempotency and no double-buy; verify actual native broker receipts before considering the PAPER safety path commissioned. Keep LIVE/V1 unchanged.
